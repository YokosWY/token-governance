### 计费口径

| 术语 | 什么意思 |
|---|---|
| **上下文 token** | 每一步都要把此前的全部内容重发一遍，重发的部分按上下文价计费。所以内容不是付一次钱就完了。 |
| **一次注入** | 某段内容进入上下文的那个动作。一次文件读取、一次技能加载、一次目录清单都算。 |
| **存活步数** | 这段内容进入之后，还剩多少步。它对账单的影响是乘数，不是加数。 |
| **存活计息**（原「重放口径」） | 本项目的核心算法：`成本 = 内容长度 × 存活步数`。只统计一次注入，结论会差两个数量级。 |
| **影子重放**（原「反事实重算」） | 把另一套配置的参数代回同一个会话，重算总价。用来做 A/B 的替代方案（配置全局，没法同场对照）。 |
| **边际口径** | 算多项措施的总收益时，每一项只在「前面几项省完」的剩余基数上计收益。上限不能直接相加。 |
| **事故会话** | 极少数把预算吃掉的会话。比如一次 68 次调用花掉 ¥91，占了该通道的七成。统计稳态收益时要把它们摘出去。 |
| **预算闸** | 达到设定的步数或金额时强制停下来让人确认，防止单个会话失控。 |

### 技能与工具

| 术语 | 什么意思 |
|---|---|
| **常驻** | 技能在模型目录里始终可见，每一步都进上下文。便利，但按步收费。 |
| **待机** | 设了 `disable-model-invocation: true` 的技能。模型调不到，文件还在，可以直接读全文，也能用 `/名字` 手动调。 |
| **旁路池**（原「待机库」） | 所有待机技能的集合。它们不占模型目录，需要时再捞。本项目把 7 个技能里的 6 个放在旁路池，只留路由常驻。 |
| **模型目录** | 模型在上下文里能看到的那份技能清单。清单越长，每一步越贵。 |
| **工具清单（schema）** | 工具的名字、参数、说明。它属于固定前缀，挂上了就每步都发，跟用不用没关系。 |
| **预设（preset）** | 一套工具与插件的组合。给专用场景单独配一套，避免重工具污染日常会话。 |
| **组合配置** | 应用启动时自动生成的最终配置。**它会被重写**，不要手改。 |
| **补丁层** | 人工维护、在组合配置之上叠加的配置。改配置改这一层。 |
| **覆盖块** | 因为预设内部不能按 id 寻址，只能整段复制过来覆盖。它是安装当天的快照，升级后要重生成。 |
| **影子实例** | 补丁里看着像本体、其实挂在已停用条目下的配置。改了不生效，还会误导人。 |
| **分组（group）** | 插件的一种打包方式。组内的条目可以被单独寻址。 |
| **隔离域（isolate）** | 提供服务能力的插件必须声明自己的域，否则整个预设加载失败。报错通常只写 `require isolate realms`。 |
| **服务型插件** | 会对外提供服务的插件（比如界面自动化）。它是有状态的单例，进预设必须带隔离域。 |

### 上下文处理

| 术语 | 什么意思 |
|---|---|
| **四项杠杆**（原「四把刀」） | 上下文瘦身的四个动作：工具清单、技能目录、工具输出、压缩。按收益从高到低排。 |
| **压缩水位** | 上下文涨到窗口的这个比例时触发压缩。太高会爆，太低会把成本花在压缩上。 |
| **回本步数** | 压缩本身有成本（压缩后第一步要按输入价重算整个新前缀）。实测约 30 步回本，剩余步数不足 30 的会话，降水位反而亏。 |
| **落盘** | 把大块工具输出写到文件，上下文里只留路径和摘要。 |
| **溢出策略** | 控制「多大的输出算大」的那组参数。本项目设为 6000 tokens。 |
| **常驻税 / 按需税** | 常驻的东西按步收税，加载的东西只在那一瞬收税。两句俗话，用来判断该把东西放哪。 |

### 流程与产物

| 术语 | 什么意思 |
|---|---|
| **准入协议** | 写操作前的一道只读关卡。按不可逆程度分三档判定：放行、待确认、拒绝，退出码与判定对应。 |
| **预检（preflight）** | 准入协议的实现脚本。只读、可重复跑，不改任何文件。 |
| **对话夹** | 一个会话一个文件夹，放会话卡、决策、日志、交接单。给长会话续跑用。 |
| **会话卡** | 对话夹里那个 ≤40 行的文件，永远只写当前状态。续跑时先读它。 |
| **里程碑** | 值得写盘的时刻：一个可验收单元完成、产生决策、上下文到 120k、踩坑修完。不是每轮都写。 |
| **交接单** | 常规会话和界面操作会话之间换手时写的文件，写清目标、当前状态、禁止动作、回传格式。 |

### 五、clarify-needs 里的词

> v0.11.1 起 `clarify-needs` 搬到独立仓库 [dsh-clarify-tier](https://github.com/YokosWY/dsh-clarify-tier)；下面这组词仍然有效，只是归属换了。

| 术语 | 什么意思 |
|---|---|
| **需求锚定（五档）** | 按锚定强度分五档决定问多深：off 不问，到 ultra 拷问到没有假设。v3.0 起替代四档 L0–L3。 |
| **前沿扫描**（原「前沿整轮」） | 每轮只问前置条件已定的那批问题，答完重算再问。 |
| **档位（off / low / high / max / ultra）** | 决定这一次要问多深。**off = 不使用本技能（退出位，不留复述与「假设」）**，low 一轮两题，high 两轮，max 三轮，ultra 用设计树问到前沿清空。 |
| **抓方向 / 厘清核心 / 挖清 / 拷问** | low、high、max、ultra 的口语叫法。 |
| **设计树** | 把讨论画成一棵决策树：每个决定会分叉出依赖它的后续决定。 |
| **前沿（frontier）** | 设计树上「前置条件已经定好、现在就能问」的那些问题。一轮只问前沿，问完等回答，再重算。 |
| **整轮提问** | 一次把整个前沿问完，而不是一问一停。每个问题都附上推荐答案，让用户回一个「是」就能推进。 |
| **共识摘要** | 深挖结束时给的清单：定了什么、为什么、否掉了哪些选项。用户确认后才动手。 |
| **锚定度 / 达标线** | 判断「问够了没有」的阈值：low ~60%（抓住大致方向）、high 80%（厘清核心方向）、max 95%（还知道怎么退、怎么验）、ultra 99%（没有默默假设）。 |
| **五维自评** | 目标、对象、边界、约束、优先级。过一遍，哪项空白就说明还没问够。 |
| **预发（pre-release）** | 能用了但还没定型，接口和档位可能改。`clarify-needs` 已不在本仓库，**已独立发布**为 [dsh-clarify-tier](https://github.com/YokosWY/dsh-clarify-tier)。 |

### 附：几个容易混的词

| 容易混 | 区别 |
|---|---|
| 常驻 / 待机 | 常驻=每步都进上下文；待机=文件在，但模型看不见清单 |
| 一次注入 / 重放成本 | 前者是动作，后者才是钱 |
| 压缩 / 裁剪 | 压缩会重写整段历史并产生固定成本；裁剪只是在压缩时顺手截断个别大块 |
| 预设 / 补丁层 | 预设是成套工具组合，补丁层是人改配置的地方 |
| 档位 / 推理 effort | v3.0 起只有档位（off / low / high / max / ultra），模式已并入档位；档名 low/high/max 与推理 effort 同名不同义 |

## 六个机制

这个包里有几套做法不是通用技巧，是从实际调优里沉淀出来的。每套都写了它解决什么问题、怎么运作、怎么验证，以及什么时候会失效。

---

### M1 · 存活计息：给上下文里的每一段内容算账

**解决什么**
看账单只知道"这周花了多少"，不知道钱花在哪。大部分人会把成本算成"注入一次的价格"，结论差两个数量级。

**怎么运作**
上下文里的内容不是付一次钱就完了，它留在历史里，之后每一步都跟着重发。所以计价单元不是"一次注入"，而是：

```
成本 = 内容长度 × 它存活的步数
```

同一份 42 KB 的技能目录，注入 53 次、每次活到会话结束，累计就是两亿 token 级的重发量。

**怎么验证**
总量 ÷ 单次长度 = 留存步数，跟日志里"注入后剩余步数 × 注入次数"对得上，就说明口径没错。

**什么时候失效**
内容只在最后几步才注入时，重放权重会很低，这时候按重放算出来的收益会显得很小——不是算错，是真的没这个收益。

---

### M2 · 影子重放：没有 A/B 也能算降幅

**解决什么**
配置是全局的，改一次要重启。同一台机器上没法让两套配置同时跑，常规 A/B 做不了。

**怎么运作**
取一个真实会话，按 step 重放，把每个模块的字符量按"存活步数"累加；再把对照配置的参数（比如工具清单 284 KB、目录 42.5 KB）代进去，重算出另一个总价。同一个会话、同样的任务、同样的输出 token，差异只来自配置本身。

**怎么验证**
脚本 `measure_modules.py` 一条命令就能复现，参数是 `--cf-schema` 和 `--cf-catalog`。

**什么时候失效**
如果两次配置之间有别的变量（换了模型、改了推理档位），反事实就会把那些影响也算进来。这种情况会标注"未分离"。

---

### M3 · 旁路池：可发现不等于可调用

**解决什么**
技能想被模型用上，就得写进目录；目录每步都要发送。装得越多，账单越贵，但真正用到的没几个。

**怎么运作**
把技能分成两层：

- **常驻**：在模型目录里，模型随时能看见、能调
- **待机**：设了 `disable-model-invocation: true`，模型调不到，但文件还在原位置

关键发现是：关掉目录可见性，不等于关掉文件可达性。需要的时候直接 `read` 那个 SKILL.md，效果和调用完全一样；用户也能用 `/名字` 手动调起。待机技能凑在一起，就是旁路池。

**怎么验证**
分层后 `read ${SKILLS_DIR}/<名>/SKILL.md` 仍能拿到全文；`skill` 工具则调不到。两个开关是独立的。

**什么时候失效**
如果某个技能要靠模型"自己想到去用"，而用户又不知道它的存在，放进旁路池等于雪藏。这类技能要么常驻，要么写进路由。

---

### M4 · 准入协议：写入前先过一道只读关卡

**解决什么**
安装、覆盖、迁移这类写操作会改动既有状态。一旦撞上已有配置，事后排查的成本远高于事前做一次探测。

**怎么运作**
所有写操作前，先跑一次只读探测，把风险按「不可逆程度」分三档：

| 判定 | 条件 | 动作 |
|---|---|---|
| 放行 | 纯新增，无同名、无占用 | 直接执行 |
| 待确认 | 同名但内容不同、目标非空、条目已存在 | 列出冲突，逐项等裁决 |
| 拒绝 | 目标被占用无法写入、探测本身失败 | 停止，不尝试绕过 |

输出是一份结构化清单：冲突类型、位置、建议动作。退出码与判定一一对应（0 放行 / 1 待确认 / 2 拒绝），可以直接接进脚本。

三条约束写进协议里：

- **只读探测自己做，写操作一律先问**，不做"猜用户会同意"的判断
- **被拒绝时不绕路**：不换路径、不提权、不改用别的方式达成同一件事
- **重复探测无副作用**，可以随时再跑一次

**怎么验证**
干净环境跑出 0 项冲突、退出码 0；冲突环境列出 N 项、退出码 1。两种都实测过。

**什么时候失效**
探测依赖路径和字段名，能认出"同名同位置"，认不出"语义重复"——两个技能名字不同、功能一样，它看不出来。这一层仍然要人判断。

### M5 · 需求锚定：先定问多深，再决定怎么问

**解决什么**
澄清有两个失败方向：问太少做错方向，问太多把人问烦。固定强度解决不了，因为任务本身的重量差得远。

**怎么运作**
四个问题给任务打分，决定档位：

| 判据 | 加分 |
|---|---|
| 要动两个以上对象，或跨目录、跨应用 | +1 |
| 不可逆（删除、覆盖、迁移、花钱、对外） | +2 |
| 只给目标、没给做法 | +1 |
| 正在纠结"要不要做 / 选哪条路" | +2 |

`0 = off`，**不使用本技能**（退出位，不留复述与「假设」）；`1 = low`，一轮两题抓方向（~60%）；`2 = high`，最多两轮厘清核心（80%）；`3 = max`，最多三轮挖清完整需要（95%）；`≥4 = ultra`，用设计树拷问到前沿清空（99%）。三条地板：不可逆至少 max；不可逆且纠结方向直接 ultra；会改文件的任务最低 low。

档位能升能降：用户说"别问了"就降到 off，"仔细点"升一档，"拷问我"直达 ultra；也可以直接点名档位，点名优先于评分；中途发现不可逆至少跳到 max。

**怎么验证**
看两件事：off/low 有没有连着问超过一轮，以及 max/ultra 的问题有没有问到边界和回滚。

**什么时候失效**
档位是模型自评的，判错的时候需要用户拨一下。所以技能里写了「用户点名优先」和降档/升档话术。

---

### M6 · 前沿扫描：一次问完当前能问的

**解决什么**
深挖时最容易犯的错是"问一个等一个"，十轮下来人已经烦了；或者反过来，一次抛十个问题，其中一半依赖另外一半的答案。

**怎么运作**
把讨论画成决策树，每个决定会分叉出依赖它的后续决定。然后找**前沿**：前置条件都已经定好、此刻就能问的那批问题。一轮只问前沿，每个问题附上推荐答案，措辞让"是"就等于采纳推荐。答完重算前沿，再问下一轮。

三条硬规则：不依赖未定答案、一轮三到五题、事实自己查决策归人。

**怎么验证**
收敛的信号是前沿为空——所有分支都走到了，没有默默假设。这时给一份共识摘要，用户确认后才动手。

**什么时候失效**
议题本身还没成形时，画不出树。这时候该退回 M5 的 high，先把要讨论什么问清。

### 附：三套配套做法

除了上面六个，还有三套辅助机制，篇幅短，合在一起说。

| 机制 | 作用 | 验证方式 |
|---|---|---|
| **自适应矩阵** | 换机器、换客户端、没有账本时，先探测 7 个维度再选降级路径 | 按矩阵逐项对，每一档都有对应做法 |
| **压缩安全阀** | 压缩有固定成本，约 30 步回本，实测净收益≈0；只用来防止爆窗口 | 压缩后第一步的 inputTokens 会等于整个新前缀 |
| **包自检** | 一条命令查结构、frontmatter、引用可达、旧词、可移植性 | `audit_pack.py` 返回 0 条即通过 |
