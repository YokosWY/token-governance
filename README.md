> 面向 LLM 代理的上下文成本治理方案。基于逐 step 用量日志定位开销来源，再通过配置层的结构性调整降低单位成本。

---



## 1. 为什么要做这个

成本的直觉判断通常指向模型单价。对一周账单做逐 step 拆解后（10,862 次调用，2.585 B 上下文 tokens），开销主体并不在模型调用本身：

| 项目 | 占上下文 | 为什么会这样 |
|---|---|---|
| 工具输出 | 34.6% | 一次 24 KB 的返回直接进上下文，之后每一步都重发 |
| 助手输出 | 27.3% | 含推理文本，高档位下推理能占九成 |
| 工具清单 | 21.0% | 每步都发；GUI 那套 56 个工具一周只用过一次 |
| 技能目录 | 12.2% | 160 个技能的描述，长会话里被注入几十次 |
| 系统提示等 | 4.9% | 固定前缀加环境注入 |

这里有个容易忽略的点：上下文里的东西不是付一次钱就完了，它会留在上下文里，之后每一步都被重新发送。一份 42 KB 的技能目录，如果在一个 490 步的会话里被注入 53 次，累计重发量就是两亿 token 级别，比任何一次「贵模型调用」都多。

所以省钱的办法其实很朴素：不需要每步都发的东西就拿出去，一次性的东西落盘，长会话在合适的位置压缩，难活交给子代理。

## 2. 改完之后的效果

以下数据由真实会话日志逐 step 复算得出，非模拟估算。方法说明与复现命令见 `docs/benchmark.md`。

| 会话 | 步数 | 改前 ¥/轮 | 改后 ¥/轮 | 降幅 |
|---|---|---|---|---|
| 长 | 492 | 0.0688 | 0.0396 | **−42.5%** |
| 中 | 333 | 0.0567 | 0.0305 | **−46.1%** |
| 短 | 41 | 0.0418 | 0.0298 | −28.7% |
| 短 | 29 | 0.0626 | 0.0478 | −23.7% |
| 短 | 27 | 0.0220 | 0.0137 | −37.7% |

一句话：每轮省 24–46%，会话越长省得越多。

拆开看 492 步那个会话，钱是这样分布的：

| 项目 | 改前 ¥ | 占比 | 改后 ¥ | 占比 |
|---|---|---|---|---|
| 技能目录 | 3.296 | 42.0% | 0.725 | 16.1% |
| 助手输出（含推理） | 1.622 | 20.7% | 1.622 | 36.0% |
| 工具清单 | 1.567 | 20.0% | 0.815 | 18.1% |
| 工具结果 | 1.285 | 16.4% | 1.285 | 28.5% |
| 用户输入 + 系统 | 0.072 | 0.9% | 0.072 | 1.6% |
| 合计 | 7.842 | 100% | 4.510 | −42.5% |

技能目录那一栏值被压到原来的六分之一以后，长会话的账单少了一半。原因不是目录本身大，而是它在会话里出现了 53 次，每次都要重发全部内容。少装几个技能，比换个便宜模型有用得多。

还没解决的也列出来：助手输出（含推理）现在是最大单项，占 36%。

## 3. 五分钟上手

不用装依赖。复制目录、改两行配置、跑一次只读体检就行。

```bash
# 1) 放进技能目录
cp -r tg/skills/tg-router ~/.dsh/skills/tg-router

# 2) 生成配置
cp tg/config.example.yaml tg/config.yaml
# 改两行：dsh_home 和 memory_root

# 3) 只读体检
python tg/scripts/cost_summary.py --config tg/config.yaml --days 7
```

体检输出大概是这样：

```
数据源: 1 个 ledger
窗口: 最近 7 天 | 合计 ¥257.71 | 9579 次调用
上下文 2.331 B | 缓存命中 98.71% | 均值 243 k/次 | ¥0.0269/次
```

装整套之前先跑一次预检，它会告诉你哪些地方会冲突：

```bash
python tg/scripts/preflight.py --config tg/config.yaml
```

预检是只读的，不动任何文件。有冲突时退出码为 1，需要逐项确认。

## 4. 里面有什么

七个技能中仅路由层常驻，其余按需启用：

| 技能 | 管什么 | 常驻 |
|---|---|---|
| `tg-router` | 入口、场景路由、冲突处理 | 是 |
| `tg-cost` | 审计、归因、算收益 | 待机 |
| `tg-context` | 工具清单 / 技能目录 / 输出 / 压缩 | 待机 |
| `tg-memory` | 对话夹、里程碑、跨区交接 | 待机 |
| `tg-orchestrate` | 子代理分档、任务书、审验 | 待机 |
| `tg-gui` | 常规区与 GUI 区交接 | 待机 |
| `tg-ops` | 补丁分层、备份、升级漂移 | 待机 |

其余六项标记为待机（`disable-model-invocation: true`）：模型侧不可见，但文件仍位于 `${SKILLS_DIR}/<名>/SKILL.md`，可直接读取或经 `/名字` 调用。

这一取舍与本项目的核心主张一致：常驻项按步计费，每增加一项都是持续的固定开销。

五个脚本都能单独跑：

| 脚本 | 作用 |
|---|---|
| `cost_summary.py` | 读账本，出总花费、通道、日均、缓存命中率 |
| `measure_modules.py` | 复算任意会话的模块花费，可做配置对比 |
| `preflight.py` | 安装前查冲突：同名技能、非空记忆根、已有补丁条目 |
| `audit_pack.py` | 包自检：结构、frontmatter、交叉引用、旧词、可移植性 |
| `check_yaml.py` | 校验补丁 YAML，自定义标签不会误报 |

## 5. 六个自研机制

以下六项机制由本项目的调优过程沉淀而来，各自附带验证方法与失效条件。完整版见 `docs/mechanisms.md`。

| 机制 | 解决什么 | 一句话 |
|---|---|---|
| **存活计息** | 算不清钱花在哪 | 成本 = 内容长度 × 存活步数 |
| **影子重放** | 配置全局，没法 A/B | 把对照参数代回同一个会话重算 |
| **旁路池** | 目录越装越贵 | 可发现和可调用是两回事 |
| **准入协议** | 怕被默默覆盖 | 写入前三档判定：放行 / 待确认 / 拒绝 |
| **分级澄清** | 问少了做错，问多了烦人 | 先定档，再决定问多深 |
| **前沿扫描** | 一问一停，或一次抛十个 | 只问前置条件已定的那批 |

三套配套做法：自适应矩阵（换环境时选降级路径）、压缩回本判据（不到 30 步别降水位）、包自检（一条命令查有没有改坏）。

## 6. 每天怎么用

| 情况 | 走哪个 |
|---|---|
| 想知道这周花了多少 | `tg-cost` |
| 会话越来越慢、越来越贵 | `tg-context` |
| 接着上次的活干 | `tg-memory` |
| 活太难，怕做歪 | `tg-orchestrate` |
| 要点界面、要截图 | `tg-gui` |
| 改完配置不对劲，或者刚升级 | `tg-ops` |

不用记命令，`tg-router` 会按场景转发。

## 7. 三条要记住的原则

其余在 `docs/principles.md`，这里挑最常用的三条。

**一、成本按「内容 × 存活步数」算。**
只统计一次注入，会得到差两百倍的结论。任何前后对比都按这个口径重算。

**二、压缩是有成本的。**
压缩后第一步要把整个新前缀按输入价重新算一遍。实测约 30 步回本，剩余步数不足 30 的会话，压低水位反而更亏。

**三、工具变少不等于省钱。**
配置生效、schema 变小、压缩触发，这些都只是过程。能不能算数，只看 cacheRead 占比、单次成本、单次上下文均值。

## 9. 配置

```yaml
dsh_home: "~/.dsh"            # 数据目录：账本、会话、配置都在里面
memory_root: "~/tg-memory"    # 对话夹根目录
skills_dir: "~/.dsh/skills"   # 技能目录

# 多套客户端时可以列出来，脚本会合并并按会话去重
# dsh_homes:
#   - "~/.dsh"
#   - "~/dsh-next"

budget:                       # 可选，超了就提醒
  daily: null

prices_usd_per_mtok:          # 可选，没有实付数据时用来折算
  input: 0.15
  cached: 0.003
  output: 0.6
```

路径支持 `~` 和环境变量，相对路径相对 `config.yaml` 所在目录。

## 10. 自检

```bash
python scripts/audit_pack.py                          # 只查本包
python scripts/audit_pack.py --also clarify-needs     # 顺带查姊妹项目
```

结果是 0 条就通过，有「高」级问题会返回非零退出码。

验收指标只有三个，其他都是过程量：

| 指标 | 期望 |
|---|---|
| cacheRead 占比 / 单次成本 | 下降 |
| 单次上下文均值 | 比如 238k 降到 180k 以下 |
| 单会话峰值 | 不再破 400k |

## 11. 做不到的事

边界先于功能。

- **改配置不等于一定生效。** 组合配置每次启动都会被重写；预设内部的参数不能按 id 寻址，只能整段覆盖，而覆盖块是安装当天的快照，升级后需要重新生成。
- **不看账单就不能宣称省了钱。** 所有优化都是过程量，结论必须回到 ledger。
- **跨客户端不保证。** Claude Code、Codex、Cursor 没有预设机制，工具隔离得改用子代理（见 `docs/adaptation.md`）。
- **不接管安全。** 密钥、脱敏、上传门禁属于各人的本地约束，不随包分发。
- **不接管需求澄清。** 那是 `clarify-needs` 的事，两边只做接口引用。

安装时的规则：只要命中「同名技能已存在 / 记忆根非空 / 已有路由工具 / 补丁条目冲突」中的任意一条，就停下来问，不自行覆盖。
