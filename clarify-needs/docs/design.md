# 设计说明

## 为什么是 4 档

| 档数 | 问题 |
|---|---|
| 2（问 / 不问） | "改个名"和"迁移 home"同档，前者过度、后者不足 |
| 3 | 缺"完全不问"，纯查询也被迫复述 |
| **4** | 正好卡在风险跳变点：只读 → 单步可逆 → 多步改配置 → 不可逆/决策 |
| ≥5 | 定档本身开始花时间，判档成本超过收益 |

**定档维度**取四个，因为它们能各自独立触发风险跳变：
对象数量（1→N）、可逆性（可逆→不可逆）、做法是否已给（给→没给）、是否在纠结方向。

## 为什么合并 grilling

三个 grill 技能的真实内容：

| 技能 | 实际内容 |
|---|---|
| `grilling` | 31 行，设计树 + 轮次 + frontier（**唯一有实体**） |
| `grill-me` | 1 行：调 `grilling` |
| `grill-with-docs` | 1 行：调 `grilling` + `domain-modeling` |

后两个是转发壳，直接吸收不丢任何东西；`domain-modeling` 保留，M3 需要时调用。

**两处冲突的处理**：
1. grilling 要求"一轮问完整个 frontier"，原文要求"一次最多 3 题" → 定为 **一轮 3–5 题**，超出说明树没拆对
2. grilling 只谈"挖想法"，原文只谈"确认需求" → 用模式区分，而非合并成一套流程

## 95% 的定义

```
90% = 我知道怎么做（每步输入/输出/失败处理都确定）
95% = 还知道怎么退、怎么验（边界、回滚、验收标准也定死，只剩执行细节）
```

判据两条：
- 有一个判断是「我觉得应该是…」→ 不到 90%
- 有一处「出问题再看」或「做完再说」→ 不到 95%

不给这个定义，抬阈值只是换个数字自欺。

## 与 TG 的分工

TG 的原则 P3 是"过程指标不是结果"。本技能**连过程指标都没有**——无法证明"问对了更省"。
所以：
- 不并入 TG 的包（否则破坏 TG "1 常驻 + 6 待机"的结构）
- 只做接口引用：`tg-router` 里一行"需求不清 → 先走 clarify-needs"
- 若将来能量化"返工率"，再考虑合并（见 roadmap）

## 已知取舍

- **95% 会增加提问轮次**：用档位对冲，L1 仍是 90%
- **L3 可能很长**：一轮 3–5 题 × 2–3 轮，用户可能疲劳；靠"一轮一问一答"和推荐答案降低负担
- **档位由模型自评**：可能判错；用户说"别问了/仔细点"可强制升降档
