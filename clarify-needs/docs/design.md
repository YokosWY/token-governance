# 设计说明

## 为什么是 5 档（v3.0 起）

v2.x 用四档（L0–L3）卡的是**风险跳变点**：只读 → 单步可逆 → 多步改配置 → 不可逆/决策。
v3.0 换成五档（off / low / high / max / ultra），卡的是**锚定度**这条连续轴：

| 档 | 锚定度 | 一句话 |
|---|---|---|
| off | — | 不问，直接做 |
| low | ~60% | 抓住大致方向 |
| high | 80% | 厘清核心方向 |
| max | 95% | 挖清完整具体需要 |
| ultra | 99% | 极致拷问 |

换轴的三个理由：

1. **风险只是锚定度的一个来源**。原四档把「风险高」自动等同「问得深」，但「改个名」这类琐事风险低、锚定度也低；而「要不要上这套架构」风险不高、锚定度极低。按风险定档会两头错。
2. **80% 这个中间态没有位置**。原来 90%（L1）和 95%（L2）挤在一起，实际差的是「知道做什么」和「知道怎么退」，中间那一档「核心方向清楚、细节可以边做边定」无处安放。
3. **档位与用户话术对齐**。用户说「大概方向就行 / 仔细点 / 往死里问」，正好是低/高/极致的自然语言刻度，不需要先翻译成 L0–L3。

**代价**：五档比四档难判。对冲手段有三条——用户可直接点名档位；评分只做初判，允许途中升降；三条地板规则（不可逆 ≥ max 等）兜住最危险的误判。

## 为什么删掉 M1–M3 模式

档位和模式是两套轴：档位说「问多深」，模式说「怎么问」。但两者实际高度相关——
low/high/max 都是「复述 + 选择题追问」，只有 ultra 才用设计树。两套轴的结果是每次都要交叉查表，
而表里只有一种有效组合。v3.0 直接把方法写进档位，`ultra` 独占设计树一节。

## 为什么合并 grilling

三个 grill 技能的真实内容：

| 技能 | 实际内容 |
|---|---|
| `grilling` | 31 行，设计树 + 轮次 + frontier（**唯一有实体**） |
| `grill-me` | 1 行：调 `grilling` |
| `grill-with-docs` | 1 行：调 `grilling` + `domain-modeling` |

后两个是转发壳，直接吸收不丢任何东西；`domain-modeling` 保留，ultra 要留档时调用。

**两处冲突的处理**：
1. grilling 要求「一轮问完整个 frontier」，原文要求「一次最多 3 题」 → 定为 **ultra 一轮 3–5 题**，超出说明树没拆对
2. grilling 只谈「挖想法」，原文只谈「确认需求」 → v3.0 用「档位差」区分：high/max 问需求，ultra 挖想法

## 锚定度怎么算

```
~60% (low)  = 知道做什么、动哪里，参数与顺序可边做边定
80%  (high) = 核心路径与关键分叉已定，只剩实现细节
95%  (max)  = 每步输入/输出/失败处理 + 边界/回滚/验收都定死
99%  (ultra)= 每条分支都有结论，没有"默默假设"
```

判据两条：
- 有一个判断是「我觉得应该是…」→ 不到 max
- 有一处「出问题再看」或「做完再说」→ 不到 max

不给这个定义，抬阈值只是换个数字自欺。

## 档名与推理 effort 撞名

`low / high / max` 同时也是模型推理 effort 的词。本技能的档说的是**锚定强度**（问用户多少），
推理 effort 说的是**想多久**（模型内部）。同名不同义，SKILL.md 末尾已显式提醒，
避免模型把「high 档」误解成「高推理」。

## 与 TG 的分工

TG 的原则 P3 是「过程指标不是结果」。本技能**连过程指标都没有**——无法证明「问对了更省」。
所以：
- 不并入 TG 的包（否则破坏 TG「1 常驻 + 6 待机」的结构）
- 只做接口引用：`tg-router` 里一行「需求不清 → 先走 clarify-needs」
- 若将来能量化「返工率」，再考虑合并（见 roadmap）

## 已知取舍

- **五档会多一次判断**：用「用户可点名 + 默认 high」对冲，日常任务根本不显式定档
- **ultra 可能很长**：一轮 3–5 题 × 2–3 轮，用户可能疲劳；靠「一轮一问一答」和推荐答案降低负担
- **档位由模型自评**：可能判错；用户说「别问了 / 仔细点」可强制升降档
- **off 有滥用风险**：限定「只给纯只读」，会改东西的任务最低 low
