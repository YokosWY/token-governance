# 需求澄清与深挖（v2.1-pre）

一件事只做一次：**在动手之前，把"要做什么"和"为什么这么做"问清楚**。
轻需求用对齐，重决策用深挖。

## 档位选择（L0–L3）

**先定档，再选模式。** 档位决定"问多深"，模式决定"怎么问"。

| 档 | 名称 | 适用 | 复述 | 提问 | 达标线 | 典型话术 |
|---|---|---|---|---|---|---|
| **L0** | 直做 | 纯查询、只读、单步 | 一句 | 不提问 | — | "多大""在不在""是什么" |
| **L1** | 快对齐 | 单步、可逆、只碰一个对象 | 一句 + 1 个确认点 | ≤1 轮、≤3 题 | 90% | "改个名""加一行""看看这个" |
| **L2** | 标准 | 多步、跨文件、改配置、装东西 | 3 确认点（要什么 / 动哪些 / 不能动什么） | ≤2 轮 | **95%** | "整理""迁移""装""优化" |
| **L3** | 深挖 | 方案、架构、不可逆、花钱、对外发送 | 先复述，再建设计树 | 多轮 frontier | 95% + 共识摘要 | "要不要做""怎么设计""值不值" |

### 自动定档（四个问题，30 秒）

1. 要动的东西 **≥2 个**，或**跨目录/跨应用**？ → +1
2. **不可逆**（删除 / 覆盖 / 迁移 / 花钱 / 对外）？ → +2
3. 用户只给了目标、**没给做法**？ → +1
4. 已经在纠结**"要不要做 / 选哪条路"**？ → +2

分数定档：**0 = L0，1–2 = L1，3–4 = L2，≥5 = L3。**

### 升降档

| 触发 | 动作 |
|---|---|
| 用户说"别问了 / 直接做 / 你自己决定" | 降到 L0，执行前标「假设：…」 |
| 用户说"仔细点 / 这个重要 / 别搞错" | 升一档 |
| 中途发现不可逆、或影响面变大 | 直接升到 L3，并说明为什么 |
| 同一问题问了两轮还没到档位线 | 走该档兜底：默认方案 + 风险 + 回滚，请用户回"按这个来" |

### 防过度澄清

- **L0 / L1 不许连问超过一轮**；能自己查的直接查。
- 档位是给你自己看的，**不必每次念出来**；只有升到 L3 时值得说一句"这事不可逆，我先确认几点"。
- 用户已经说清的细节，任何档位都不要再确认。

## 模式选择（M1–M3）

| 模式 | 什么时候用 | 成本 | 产出 |
|---|---|---|---|
| **M1 对齐**（默认） | 用户在派活：含糊、多步、会改东西 | 低（1–2 轮） | 一句话复述 + 3 个确认点 |
| **M2 深挖** | 用户在纠结：方案、架构、选型、路线、想法 | 中（多轮） | 完整决策树 + 每条分支的结论 |
| **M3 深挖+文档** | 深挖的结论需要沉淀下来给以后看 | 中高 | 决策记录（ADR）+ 术语表 |

判断口诀：**"你要我做什么" → M1；"我这么想对不对" → M2；"以后还要照着做" → M3。**

和档位的对应：**L0–L2 用 M1；L3 用 M2；L3 且结论要留档用 M3。**
用户说"别问了/直接做/你自己决定"→ 立刻停，按最佳理解执行，开头标一行「假设：…」。

## M1 · 对齐（默认模式）

### 1. 开头强制复述

不做客套，一句话说完：

> 你要的是「<目标>」，我打算「<做法>」，范围是「<对象>」，对吗？

复述强度按风险分档：

| 任务类型 | 复述强度 |
|---|---|
| 只读、单步（看下磁盘、读个文件） | 一句话复述，直接做 |
| 多步、会改文件/配置 | 复述 + 3 个确认点（要什么、动哪些、不能动什么） |
| 不可逆（删除、迁移、改系统、花钱） | 复述 + 选项确认 + 回滚方案 |

### 2. 自评五维

心里过一遍（不一定要输出），任何一项空白就说明没到 95%：

| 维度 | 问自己 |
|---|---|
| 目标 | 最终要什么结果？成功长什么样？ |
| 对象 | 具体哪些文件 / 目录 / 应用 / 账号 / 工作区？ |
| 边界 | 哪些不能动？只读还是可改？哪些必须保留？ |
| 约束 | 时间、预算、凭据、正在运行的进程、不可逆风险 |
| 优先级 | 速度优先还是安全优先？出问题先保哪个？ |

### 3. 95% 的判据

> 达标线按档位取：**L1 = 90%，L2 / L3 = 95%**。

**能不猜地写出执行步骤，每步的输入、输出、失败处理都确定** → 才到 90%。
**而且边界、回滚、验收标准也都定死，剩下的只有执行细节** → 才到 **95%**。

差的那 5% 是什么：90% 只保证"我知道怎么做"，95% 还要求"出错我知道怎么退、做完我知道怎么验"。
- 只要有一个判断是"我觉得应该是……" → 不到 90%
- 只要有一处"出问题再看"或"做完再说" → 不到 95%

### 4. 提问规则

- 用 `ask_user_question`，**一次最多 3 题**
- 每题 2–4 个选项，**第一项标（推荐）**，并写一句该选项的代价
- 选项必须具体到可执行（路径、动作、数据去向），不要"是 / 否"这种空问题
- 一轮问完三类缺口：**范围**（动哪些）、**成功标准**（怎么算完成）、**禁区**（不能碰什么）
- 两轮后仍不到 95%：给出**默认方案 + 风险 + 回滚方式**，请用户回一句"按这个来"

### 5. 不该问的

- **能自己查的事实**（文件在不在、配置值、版本号、进程状态）→ 先查，再带着结论问
- **纯查询**（"这个文件多大"）→ 复述一句直接动手
- 用户已经说清的细节，不要重复确认

### 6. 必须停手确认的动作

删除 / 移动 / 覆盖、改系统配置与注册表、动正在运行的程序、花钱、对外发送、批量重命名、改工作区或账号绑定。

### 7. 执行中出现新歧义

不要自己补设定。停下来一句话问：「发现 X，影响 A/B 两条路，你要哪条？」——同样给选项。

## M2 · 深挖（设计树）

适合：方案能不能行、要不要选这条路、这个架构合不合理、要不要投入。
**目标不是"让用户同意"，而是把所有隐含假设挖到台面上。**

### 1. 设计树与 frontier

把讨论画成一棵**设计树**：每个决策会分叉出依赖它的后续决策。

- **frontier（前沿）** = 所有**前置条件已定**的决策，也就是此刻就能问、不用猜后续答案的问题。
- 一轮把**整个 frontier** 问完，然后停下等回答；下一轮重算 frontier。

### 2. 每轮格式（照抄）

```
❓ **Q1** - **<问题标题>**：<问题正文，可含多段、可给多选>

➡️ <我的推荐答案>

---

❓ **Q2** - **<问题标题>**：<问题正文>

➡️ <我的推荐答案>
```

两条硬规则：

1. **措辞要让"是"等于接受我的推荐**（用户回一个"是"就能推进）。
2. **依赖仍未定问题的问题，属于下一轮**，不许混进本轮。

一轮控制在 **3–5 题**；超过就说明树还没拆对，先砍分支。

### 3. 事实我查，决策归你

- **事实**（文件、配置、依赖、性能数据）→ 我自己查；需要耗时调查就派子代理，不要问用户。
- **决策** → 只能问用户，并等回答。
- **不阻塞**：某个子代理还在查，只有**下游**问题等它；其余问题照常本轮问。

### 4. 完成条件

**frontier 为空** = 每条分支都走到了，没有任何"默默假设"。
此时给一份**共识摘要**（决策清单 + 各自的理由 + 被否决的选项及原因），
并明确问一句「以上是否就是你的意思？」——**用户确认前不动手**。

## M3 · 深挖 + 文档

在 M2 基础上，把结论落到文件（边问边写，别等结束再补）：

| 产出 | 触发 | 格式 |
|---|---|---|
| **ADR**（决策记录） | 做了一个以后不好改的决定 | `docs/adr/NNNN-<标题>.md`：背景 / 选项 / 结论 / 后果 / 回滚 |
| **术语表** | 出现"同一个词两种意思"或新造词 | `GLOSSARY.md`：词条 / 定义 / 别称 / 反例 |
| 设计树快照 | 结论多、分支深 | 附在 ADR 末尾，画成缩进列表 |

需要完整方法论时调 `domain-modeling` 技能；文件已存在就先读再改，不要覆盖别人的记录。

## 正例

**例 1（含糊需求 → M1）**
用户：「帮我把 ~/projects 整理一下」
→ 复述 + 问 3 题：两套 DSH 各占一个文件夹？子智能体统一目录？备份留几天？
→ 拿到答案再动。

**例 2（迁移 → M1 重档）**
用户：「把 home 搬过来」
→ 先查：目录多大、有没有 junction、谁在引用、怎么回滚
→ 再问：搬不搬、旧路径留不留链接、出问题回滚到哪一步。

**例 3（方案纠结 → M2）**
用户：「这套 token 治理要不要上」
→ 第一轮 frontier 三问：
  1. 目标是把账单压到多少？（推荐：先定 30% 降幅，可验）
  2. 允许改配置文件吗？（推荐：允许，但先备份）
  3. 出问题回滚到什么状态？（推荐：回到上一版 patch）
→ 用户答完再展开下一层：分几个阶段、先做哪项、验收指标。

**例 4（要留档 → M3）**
同一议题反复讨论第三次 → 边问边写 ADR，把"为什么否掉 A、选了 B"记下来，下次不用重吵。

## 反例

- 用户说「整理一下」，直接开始移动目录 → 打断 junction / 快捷方式，返工两次。
- 用户说「搬过来」，只问"要不要搬"，没问"旧路径留不留" → 后续新建会话失败。
- 明摆着能自己查（文件是否存在），却问用户「那个文件在吗」。
- 深挖时一次抛 10 个问题 → 用户疲劳，只回前两个，后面的全成了默认假设。
- 把"事实"和"决策"混在一起问 → 用户被迫替你查资料。

## 收尾

无论哪种模式，**确认后把最终理解用 1–3 行钉在任务开头**（目标 / 对象 / 成功标准），
后续按它验收；中途需求变了，重走一次复述。
