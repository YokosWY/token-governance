# clarify-needs · 需求澄清与深挖

> 动手之前先对齐需求：轻量任务快速确认，重度决策深挖到底。
> **独立项目**，不并入 Token-Governance（TG）——两者是上下游关系，不是同一件事。
> **预发布**：随 TG 仓库一起分发，接口和档位还没定型，升级可能不兼容。

- 版本：**v2.1-pre**（预发：接口与档位可能调整）
- 技能名：`clarify-needs`（常驻，模型目录可见）
- 结构：1 个技能 + 3 篇文档 + 变更史

---

## 1. 它解决什么问题

Agent 最贵的开销不是"想太多"，而是**想错了重做**：方向错了 → 全部推倒 → 上下文重放再来一遍。
这类成本通常比任何压缩优化的收益都大一个量级。

| 症状 | 代价 |
|---|---|
| 说法含糊（"整理一下""优化下"） | 做错方向，全量返工 |
| 方案没想清就开工 | 做到一半发现路不通 |
| 关键假设没人说出来 | 交付时才发现不是用户要的 |
| 只问"要不要"，不问"旧路径留不留" | 后续步骤全崩 |

本技能把"问清楚"变成有档位、有格式、有停止条件的流程，而不是靠临场发挥。

---

## 2. 三个层次：档位 / 模式 / 达标线

### 档位（怎么定量）

| 档 | 适用 | 复述 | 提问 | 达标线 |
|---|---|---|---|---|
| **L0 直做** | 纯查询、只读、单步 | 一句 | 不问 | — |
| **L1 快对齐** | 单步、可逆、只碰一个对象 | 一句 + 1 确认点 | ≤1 轮 ≤3 题 | 90% |
| **L2 标准** | 多步、跨文件、改配置、装东西 | 3 确认点 | ≤2 轮 | **95%** |
| **L3 深挖** | 方案、架构、不可逆、花钱、对外 | 复述 → 设计树 | 多轮 frontier | 95% + 共识摘要 |

**定档**：四个问题，半分钟。

| 问题 | 加分 |
|---|---|
| 要动 ≥2 个对象，或跨目录/跨应用 | +1 |
| 不可逆（删除 / 覆盖 / 迁移 / 花钱 / 对外） | +2 |
| 用户只给目标、没给做法 | +1 |
| 已在纠结"要不要做 / 选哪条路" | +2 |

`0 = L0，1–2 = L1，3–4 = L2，≥5 = L3`

### 模式（怎么问）

| 模式 | 方法 | 用于 |
|---|---|---|
| **M1 对齐** | 强制复述 + 五维自评 + 选择题追问 | L0–L2 |
| **M2 深挖** | 设计树 + frontier + 整轮提问（吸收自 `grilling`） | L3 |
| **M3 深挖+文档** | 边问边产 ADR / 术语表（吸收自 `grill-with-docs`） | L3 且要留档 |

### 达标线（什么叫够）

```
90% = 我知道怎么做（每步输入/输出/失败处理都确定）
95% = 还知道怎么退、怎么验（边界、回滚、验收标准也定死，只剩执行细节）
```

- 有一个判断是「我觉得应该是…」→ 不到 90%
- 有一处「出问题再看」或「做完再说」→ 不到 95%

## 3. 快速开始

无需安装脚本，复制目录即可：

```bash
cp -r clarify-needs ~/.dsh/skills/clarify-needs
```

装好后模型目录会出现 `clarify-needs`。它是**常驻**技能（每个请求都在上下文里），
所以不需要手动触发——但你要主动用深挖时，可以直接说「grill 我」/「拷问我这个方案」。

---

## 4. 典型场景

| 场景 | 会走哪条 |
|---|---|
| "帮我把 ~/projects 整理一下" | L2 + M1：复述 + 3 个确认点（范围 / 成功标准 / 禁区） |
| "把 home 搬过来" | L2+ + M1 重档：先查 junction/引用/回滚，再问留不留旧链接 |
| "这套 token 治理要不要上" | L3 + M2：设计树，第一轮问清目标/权限/回滚 |
| 同一议题第三次讨论 | L3 + M3：边问边写 ADR，把"为什么否掉 A"记下来 |
| "这个文件多大" | L0：直接查，一句话答完 |

## 5. L3 深挖长什么样

每轮把**整个 frontier**（前置已定的那些决策）问完，格式固定：

```
❓ **Q1** - **问题标题**：问题正文

➡️ 我的推荐答案

---

❓ **Q2** - **问题标题**：问题正文

➡️ 我的推荐答案
```

三条硬规则：

1. 措辞让"是"等于接受推荐答案（回一个"是"就能推进）。
2. 依赖未定问题的问题属于**下一轮**，不许混进来。
3. **事实我查、决策归你**：能自己查的不问用户；需要调查就派子代理，且只有下游问题等它。

结束条件：**frontier 为空** → 给共识摘要（决策 + 理由 + 被否选项）→ 用户确认后才动手。

## 7. 设计取舍（详见 `docs/design.md`）

| 决定 | 理由 |
|---|---|
| **4 档**，不是 2/3/5 | 正好卡在风险跳变点：只读 → 单步可逆 → 多步改配置 → 不可逆；5 档以上定档成本超过收益 |
| **合并三个 grill 技能** | `grill-me` / `grill-with-docs` 实为转发壳，实体只有 `grilling`（31 行）；吸收不丢内容 |
| **一轮 3–5 题** | grilling 要求"一轮问完 frontier"，原规则限制"一次 3 题"，取交集 |
| **L1 保持 90%** | 95% 会明显增加轮次；用档位对冲，日常小改不被追问 |
| **不并入 TG** | TG 只认可度量；本技能拿不出指标，硬合并会破坏 TG 的"1 常驻"结构 |

## 8. 成本

| 项 | 值 |
|---|---|
| SKILL.md | 10.3 KB / 4,645 字符 ≈ **1,161 tokens** |
| 周重放（1 万步量级） | ≈ 12.6 M tokens |
| 缓存命中时 | ≈ ¥0.26/周（可忽略） |
| 未命中时 | ≈ ¥13.5/周（最坏情况） |

**真正的成本不是 token，而是多问一轮带来的行为开销**——这由档位控制（L0/L1 不问）。

---

## 9. 已知边界

做不到的

- 无法证明"问对了更省"：这是**不可度量**的收益，只能靠少返工间接体现。
- 定档由模型自评，可能判错；靠用户"别问了 / 仔细点"强制升降档兜底。
- L3 可能很长（2–3 轮 × 3–5 题），用户疲劳时收敛质量会下降。

不做的

- 不接管方案评审、代码评审（那是别的技能的事）。
- 不做成多技能包（必须单技能常驻，否则目录成本上升）。
